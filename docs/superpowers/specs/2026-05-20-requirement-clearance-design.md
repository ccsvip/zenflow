# 需求消项跟进能力设计

## 背景

飞书 Base `项目关键需求和问题消项表` 记录了 20 条项目关键需求/问题，字段包含模块、问题描述、类型、重要程度、紧急程度、研发回复、解决方案、时间节点、处理结果和备注等。当前 ZenFlow 已具备项目、需求、任务、Bug、成员和 PostgreSQL 持久化能力，但需求池字段偏 Story 管理，缺少“消项跟进”所需的结构化信息和视图。

## 目标

将 ZenFlow 的需求池增强为可承接“项目关键需求和问题消项表”的跟进工具，让团队能按紧急程度、类型、研发回复和处理结果快速识别未消项问题。

## 非目标

- 不实现数字人行走播报、人脸识别、巡逻模式等具体业务功能。
- 不直接接入飞书 Base 实时同步。
- 不新增 TypeScript、状态管理库或新的 UI 框架。
- 不重构 `main.jsx` 为多文件组件，除非后续用户单独要求。

## 信息架构

在现有 `requirements` 模型上新增消项字段：

| ZenFlow 字段 | 飞书 Base 字段 | 用途 |
| --- | --- | --- |
| `module` | 模块 | 标记问题所属模块 |
| `requirementType` | 类型 | 区分功能不完善、设计缺陷、高阶功能 |
| `importance` | 重要程度 | 标记是否重要 |
| `urgency` | 紧急程度 | 标记紧急/非紧急 |
| `devReply` | 研发回复 | 记录研发侧当前答复 |
| `solution` | 解决方案 | 记录拟定解决路径 |
| `milestone` | 时间节点 | 记录计划节点 |
| `result` | 处理结果 | 记录消项结果 |
| `remark` | 备注 | 补充说明 |

保留现有 `title`、`description`、`stakeholder`、`projectId`、`priority`、`status`、`attachments` 字段。飞书中的“问题描述”映射到 `description`，模块名可作为默认标题的一部分，但 UI 中仍允许单独编辑标题。

## 交互设计

需求池顶部新增消项视图筛选：

- `全部`：显示所有需求。
- `待研发回复`：`devReply` 为空且 `result` 为空。
- `紧急事项`：`urgency === '紧急'` 且未消项。
- `未消项`：`result` 为空。
- `高阶功能`：`requirementType === '高阶功能'`。

需求表格展示新增列：模块、类型、紧急程度、研发回复、处理结果。详细字段在新建/编辑需求弹窗中维护。为控制表格宽度，解决方案、时间节点、备注放在卡片式摘要和弹窗中，不作为主表固定列。

## 数据流

1. 前端通过 `/api/data` 拉取需求数据。
2. `lib/dataRepository.mjs` 返回新增字段。
3. 创建/更新需求时，`main.jsx` 将新增字段提交到 `/api/requirements`。
4. `lib/db.mjs` 在初始化时为旧数据库添加新增列，保证已有部署可平滑升级。

## 错误处理与兼容

- 旧记录缺少新增字段时，前端展示为空字符串。
- 后端使用 `asText` 兜底，避免 `null` 破坏输入框受控状态。
- 迁移使用 `ALTER TABLE requirements ADD COLUMN IF NOT EXISTS`，不破坏已有数据。

## 测试策略

- 扩展现有 Node 测试，断言数据库迁移包含新增字段。
- 断言仓储层 SQL 返回并写入新增字段。
- 断言需求池包含消项视图筛选和新增表单字段。
- 运行 `pnpm test` 和 `pnpm build` 验证基础质量。

## 范围确认

本次实现聚焦“需求消项跟进能力”。飞书 Base 的 20 条记录可作为后续导入数据来源，但本次不自动写入数据库，避免在用户现有环境中制造隐式数据。
